# 游戏项目方案制定与任务拆解（Unreal Engine）

## 何时使用
- 有游戏设计文档/需求，需要拆成可实现的 UE 开发任务
- 一个玩法功能太大、太模糊、无法开工
- 需要把工作并行分配给多个 agent/美术/程序
- 需要向人沟通范围与排期
- 实现顺序不明确

**不适用**：单文件小改动、规格已含明确任务、纯内容批量导入（无逻辑依赖）。

## 任务三型模型

游戏任务分三类，验证方式不同：

| 类型 | 定义 | 示例 | 验收证据 |
|---|---|---|---|
| **code** | 引擎/玩法逻辑 | GAS Ability、网络复制、UI Widget | 测试/build |
| **asset** | 资产制作与管线 | 高模→LOD→导入、动画状态机、材质 | 引擎内检查/build + 资产校验 |
| **game-feel** | 手感与体验调优 | 打击感、摄像机阻尼、输入缓冲 | playtest + 性能预算 |

## 流程

### 1. 只读规划模式
先读：GDD/需求、现有 UE 项目结构（Module/Class/资产目录）、现有蓝图与 C++ 约定、内容管线。**规划期间不写实现代码**。产出 `tasks/plan.md` + `tasks/todo.md`。

### 2. 建立依赖图（双链）
同时考虑**引擎系统依赖**与**资产管线依赖**：

```
（代码链）                 （资产链）
InputComponent             BaseMesh（高模）
    │                          │
    ├── GameplayAbility    SkinnedMesh（低模）
    │       │                  │
    │       ├── AnimationState   AnimSequence（动画）
    │       │        │           │
    │       │        └── VFX/音频    Montage（含通知）
    │       └── ...
    └── UI（HUD 显示）
```

- 代码链：按底层→上层（Actor→Component→Ability→UI）
- 资产链：高模→LOD→导入→材质→动画骨架依赖（**先骨架再动画**）

### 3. 垂直切片（按玩法路径切）
不要水平切（先全部资产→再全部逻辑→再全部 UI）。每任务是一条**完整可玩路径**：

- 任务1：玩家可以移动（Character Movement + 输入 + 基础动画）
- 任务2：玩家可以攻击（GAS Ability + 动画 Montage + 命中判定 + 敌人受击）
- 任务3：玩家可以被打败（生命值 + 死亡 + 重生）

### 4. 写任务（每任务含验证证据）

```markdown
## Task [N]: [标题]

**类型:** [code | asset | game-feel]
**描述:** 一段说明
**验收标准:**
- [ ] 可观测、可断言的条件
**验证证据:**
- [ ] [test] 通过：<具体命令/测试套件>
- [ ] [build] UE 编辑器/打包无错误
- [ ] [playtest] 录像/会话记录 + 手感参数
- [ ] [perf] 帧率/内存预算：<目标值>
**依赖:** Task [N-1]
**涉及文件/资产:** <.cpp/.h/.uasset 路径>
**预估范围:** [XS | S | M | L]
```

**手感验收转译表**（把主观转成可断言参数）：
- "打击感好" → hitstop 帧数(如 3-5)、命中停顿、TTK 值、命中反馈延迟
- "移动手感好" → 加速度曲线、转向阻尼、跳跃缓冲窗口帧数
- "摄像机稳" → 阻尼参数、FOV 变化幅度、碰撞半径

### 5. 排序与 Checkpoint
1. 依赖满足（地基先行：先骨架后动画、先输入后能力）
2. 每任务后系统可编译/可运行
3. 每 2-3 任务设 checkpoint（build 通过 + 核心玩法可玩 + 人工 review）
4. **高风险任务前置（fail-fast）**：核心玩法手感验证优先于内容填充

## 尺寸分级（游戏版）

| 尺寸 | 范围 | 示例 |
|---|---|---|
| XS | 单个函数/单个资产 | 加一个 Attribute |
| S | 1-2 文件/资产 | 一个 Actor/一个蒙太奇 |
| M | 3-5 文件/资产 | 一条完整玩法切片 |
| L | 5-8，多系统 | 带网络复制的技能系统 |
| XL | 过大——必须再拆 | — |

**再拆信号**：超一个专注会话、验收标准写不出 3 条、触及两个以上独立子系统（如技能+网络）、任务标题含"和"。

## 并行化判定
- **可并行**：独立玩法切片、已实现功能的测试、资产库（无依赖的高模/贴图）
- **必须串行**：资产管线链（骨架→动画）、数据库/状态迁移、依赖链
- **需协调**：共享 API 契约（先定契约再并行，如技能与 UI 的接口）

## 反例（不要这样）
- 没有书面任务清单就开工
- 把所有资产当"文件数"按代码任务拆（应标 asset 型）
- 手感任务没有 playtest 证据就说"done"
- 用"build 通过"作为手感任务的唯一验证
- 先堆全部资产再做玩法（违反垂直切片）
- 把 L 级任务直接展开不拆

## 验收
- 每任务有验收标准 + 验证证据（四类之一）
- 依赖图包含代码链与资产链
- 垂直切片可独立试玩
- 任务清单已记录，人工已审阅
- 高风险（核心手感）任务已前置
